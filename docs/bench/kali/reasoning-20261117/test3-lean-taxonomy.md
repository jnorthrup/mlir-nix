## Findings

Every number is a run in the tables below (`logs/run/<run>.json`, `.out`, `.err`). Wall times are on a shared machine:
another task's Lean/Vampire builds ran concurrently (1-min load average 1 to 12, the `load` column), so user CPU
time is the steadier figure, and even it moves: Enum_plain_1000 took 25.5 s wall / 34.2 s user at load 7 and
15.7 s / 23.4 s at load 1.4 (bprof run). Peak RSS is ru_maxrss in MiB. Limits on every run: 20 min wall, 6 GiB resident set (run.py's watchdog, sampled every
0.1 s, SIGKILL), start only with MemAvailable >= 8 GiB. `systemd-run --user` is unavailable over ssh on Kali, and an
address-space cap cannot stand in for a memory cap: lean 4.36 aborts at start under `prlimit --as` 6.5 GiB ("failed to
create thread"; it reserves ~3.4 GiB of address space idle and reached 11 GiB VmSize on a 10-constructor file), so
RLIMIT_AS is only a 32 GiB backstop.

**Input.** mlnix on onto.nix gives the expected answer (forms 201,007; classes 9,045; ancestorLinks 90,404; things
21,691; relations 1,765) in 2.5 s; taxonomy.nix returns the table itself (class names, ancestor lists; 1.6 MB JSON).
crosscheck.py, an independent Python S-expression reader over the 78 pinned files, gives the same counts, the
identical class list and identical ancestor lists (9,040 classes with ancestors, 90,404 links, same order): AGREE.

**Encoding A, the taxonomy as a data table** (`classNames : Array String`, `links : Array (Nat × Nat)` of indices):
- As a plain source literal (`def … := #[…]`, SumoTaxA.lean, 1.4 MB), Lean 4.36.0 rejects it with default options
  after 70 s: `maximum recursion depth has been reached` on the 9,045 names and `(deterministic) timeout …
  maxHeartbeats (200000)` on the links. Prefixes put the recursion limit between 2,000 and 4,000 elements for either
  literal (slicedef-*).
- With both limits lifted (maxRecDepth 10^6, maxHeartbeats 0) it ran 975 s and was killed at the 6 GiB cap: no
  .olean (a2-lean). Prefixes of the links literal: 1k/2k/4k/8k/16k links take 2.8/5.5/11.2/24.7/65.7 s and give
  2.5/5.0/9.9/19.6/39.1 MB of .olean (about 2.4 KB per link); at 16k the IR compiler alone takes 19.6 s. Ascribing
  each pair `((a, b) : Nat × Nat)` changes it little (16k: 53 s against 66 s).
- The same file with `noncomputable def` (no code generation, SumoTaxANC.lean) builds: 224 s, 4,423 MiB peak,
  13.2 MB .olean. Of that, elaboration is 3.2 s (names) + 161 s (links); the kernel's type check is 0.6 s; leanchecker
  replays it in 1.7 s (empty module 1.0 s).
- Built as kernel terms directly (TaxLoader.lean reads names.txt/links.txt, builds the Exprs, `addDecl`; no
  elaborator, no compiler; SumoTaxK.lean): 4.7 s, 1,751 MiB, 11.6 MB .olean, against 1.6 s and 1,568 MiB for the
  `import TaxLoader` baseline (it imports Lean): about 3.1 s and 183 MiB for the table. leanchecker: 2.2 s.
- As two string literals split at run time (SumoTaxBlob.lean): 0.6 s, 492 MiB, 1.1 MB .olean; but the kernel cannot
  see the table through `String.splitOn`, so its theorems need `native_decide` (1.5 s). Each such theorem then rests on
  an axiom that native_decide adds, e.g. `links_size._native.native_decide.ax_1_1`, so it trusts the compiler
  (audit-SumoTaxBlobThm).
- Proofs about the table, decided by the kernel (`decide +kernel`; 8 theorems: both sizes, every link in range and
  irreflexive, Human→Entity at link 38,371, Human→Entity by membership, the last link by a full scan, two name lookups):
  67.6 s and 1,961 MiB over SumoTaxANC (kernel time per theorem 0.8 to 18.5 s), 101 s and 3,759 MiB over SumoTaxK (its
  chunked lists joined by List.append reduce more slowly); leanchecker re-checks SumoTaxKThm in 103 s. `#print axioms`:
  six of the eight depend on no axioms, and the two membership theorems on propext, Classical.choice and Quot.sound
  only (audit-*). Proving the name lookups by `rfl` instead stops at maxRecDepth (k-thm); `decide +kernel` leaves the
  work to the kernel.

**Encoding B, the taxonomy as one inductive type** (the first N classes, `inductive SumoClass | «Abdomen» | …`):
- Enumeration, default options: N = 10/40/100/400/1,000 builds in 0.5/0.6/1.1/4.7/25.5 s with .olean
  0.09/0.32/1.05/9.9/53.5 MB. At N = 2,000 and 4,000 the declaration itself, with no deriving, stops with
  `(deterministic) timeout at whnf, maximum number of heartbeats (200000)` (81 s, 296 s). At N = 9,045 it was killed by
  the 20-min timeout (1,200 s wall, 1,177 s user, 4,320 MiB), still inside the `inductive` command, no message.
- With maxHeartbeats 0 it builds at N = 2,000 (82 s, 1,886 MiB, 203 MB .olean) and N = 4,000 (390 s, 5,536 MiB,
  790 MB .olean; with deriving DecidableEq 477 s, 5,582 MiB, 795 MB). The .olean grows as N² (53.5 → 203 → 790 MB per doubling ×3.8, ×3.9); extrapolated, N = 9,045 would
  be about 4 GB of .olean, more than the 6 GiB cap and over 30 min (an extrapolation, not a run).
- Where the time goes at N = 1,000 (bprof-*, trace.profiler): the `inductive` command takes 12.2 s. Of that, 2.2 s is
  the kernel's check of SumoClass and 1.4 s is SizeOf; the remaining ~8.6 s are steps under 0.2 s each. The
  auxiliary `SumoClass.ctorElim` adds a 2.15 s kernel check and 3.3 s of compilation.
- `deriving DecidableEq` on the enumeration costs little where the type builds (N = 1,000: 28.6 s against 25.5 s;
  N = 2,000 with heartbeats lifted: 80.5 s, 205 MB). It is not the bottleneck: the inductive type is. The
  deriving-at-9,045 run was stopped by hand after 33 s, because deriving starts only after the declaration, which did
  not finish in 20 min (benum-deceq-9045.note).
- Constructors with one field (`| «Human» (x : Nat)`, the case of lean4 #10152's 2025 benchmark): the old quadratic
  DecidableEq construction (deriving.decEq.linear_construction_threshold raised) takes 0.8/1.6/7.9 s at
  N = 10/20/40 and hits the heartbeat limit at N = 100, 400 and 1,000 (5,204 MiB at 1,000), which reproduces "timed out
  past 30-40 constructors". The linear construction that Lean 4.36 uses by default takes 0.8/0.7/0.9/2.2 s at
  N = 10/20/40/100. Beyond that, no deriving matters: from N = 400 the declaration is rejected with `tag for
  constructor 'SumoClass.AmbienceAttribute' is too big, this is a limitation of the current runtime`. AmbienceAttribute
  is class index 244, and LeanMaxCtorTag is 243 in lean.h, so an inductive type can have at most 244 constructors
  with fields.

**For the claim.** The scaling risk is real, and the bottleneck is not where the claim puts it. With 4.36's linear
construction, deriving equality is cheap. The cost is the inductive declaration itself: its .olean grows as N², it
passes the default heartbeat limit between 1,000 and 2,000 constructors, and 9,045 does not finish in 20 min. With
fields, the runtime limit of 244 constructors makes one inductive type impossible.

The taxonomy fits Lean as a data table, but only if the table reaches the kernel as terms (3.1 s, 11.6 MB) or as
`noncomputable` source (224 s, 4,423 MiB). A computable `#[…]` literal does not build within 16 min and 6 GiB. As in
test 1, the elaborator and the code generator are the costs; the kernel checks the whole table in 0.6 s. Proofs about
the table, checked by the kernel, take 0.8 to 18.5 s each over the 90,404-link list.
