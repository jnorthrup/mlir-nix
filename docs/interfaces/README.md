# The C++ interfaces

Generated by `scripts/cxx-interfaces.py` from a build's translation units, each compiled again with its own flags to
LLVM IR ("aarch64-unknown-linux-gnu").  Do not edit: run it again.

A component is a CMake target.  An interface is a function or variable one component defines and another uses.  Its ABI
is the signature the compiler gave it: what a lowered implementation must define so the C++ callers keep linking, and
what a lowered caller declares (`<component>.mlir` has each component's interface as `llvm.func` declarations).  What it
needs is what its code reaches inside its translation unit, through the unit's own helpers:

- **C**: libc and the system only (and other interfaces): it can be written in MLIR's dialects now, calling libc as mlnixci does;
- **C++ rt**: the C++ runtime as well: new/delete, `std::`, exceptions (a throw or a landing pad): those go first;
- **MLIR API**: MLIR's or LLVM's C++ classes: compiler code, whose lowering is to declarations (ODS, IRDL, PDL), not to code.

## Const audit (the hand-written runtime's interface methods)

Only NixEval, NixStore, NixFrontend and the tools: the dialect libraries (MLIRNix, MLIRTrikeShed) are MLIR's
API and lower to declarations, not const-ification.  The signal is clang's own: at the build's optimization
level it marks a method's `this` parameter `readonly`/`readnone` when the method cannot mutate the object.
reads-only = clang proved `this` read-only; may-mutate = it did not.  A reads-only method not yet declared const
is a candidate to REVIEW, not an automatic change: physical read-only of `this` is not logical const.  A method
that mutates state through a member pointer (Store::deletePath, ensurePath, addTextToStore, registerValidPath, ...)
is physically reads-only here but logically mutating, and must NOT be made const.  Pure readers (showType,
isValidPath, queryPathInfo, allValidPaths, queryReferrers, resolveExprPath, ...) are the real candidates.  The fix
lane decides each and confirms by adding const and rebuilding.
